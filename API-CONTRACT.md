# MyCodeScan — API contract

**This file is the single source of truth for the MyCodeScan backend.**

Two front-ends are already written against it, byte for byte:

- `mycodescan/` — the phone scanner app (this folder).
- `MyStokio` → `src/lib/codescan.ts` — the billing-side client that lists scans, reads
  them onto a bill, and deletes them afterwards.

**Authentication is shared.** Section 3 documents the `/api/v1/auth` router both apps sign in
against, so one account works in both and a scan made on the phone is readable at the counter.
If you already run that router, only section 5 is left to build.

Hand this document to whoever (or whatever) builds the backend. If the server matches
what is written here, both front-ends work with no changes. **Do not edit this file to
match a server that drifted** — fix the server, or change this file and both clients
together, deliberately.

A working reference implementation lives in `mycodescan/server-reference/`. It is not
production software — no password hashing beyond scrypt, no clustering, JSON-file
storage — but it implements every endpoint below exactly, so it can be used to develop
against and to settle any question this document leaves ambiguous.

---

## 1. What the system does

A shopkeeper walks around the shop with a phone, scanning barcodes into a **scan
session**. Each session has a short human-readable **scan ID** such as `SC-7QK2M`.

Later, at the billing counter on a PC, they open MyStokio → New Sale → **MyCodeScan**,
see their sessions listed, pick one, and every barcode in it is added to the bill.
When the invoice is saved, MyStokio deletes the session.

The backend is therefore a small, short-lived holding area for barcode lists. It is
**not** a product catalogue and **not** a copy of the shop's data. It never sees prices,
customers or invoices — only barcode strings and quantities.

That boundary is deliberate and should be preserved: MyStokio's whole promise is that
shop data stays on the shop's own machine. A barcode number on its own is not shop
data in any meaningful sense; a product list with cost prices would be.

## 2. Conventions

| Thing | Rule |
| --- | --- |
| Base URL | A configurable host, e.g. `https://financegpt-backend-phm6.onrender.com/`. Paths below are relative to it, and clients tolerate a base with or without a trailing slash |
| Versioning | Both surfaces are versioned: `api/v1/auth/...` and `api/v1/scans/...`. Auth was unversioned in an earlier revision of this document; it is not any more |
| Format | JSON request and response bodies, `Content-Type: application/json` |
| Encoding | UTF-8 |
| Timestamps | ISO 8601 with `Z`, e.g. `2026-08-18T06:14:22.418Z`. Always UTC |
| Auth | `Authorization: Bearer <token>` on every scan endpoint and on `api/v1/auth/me` and `api/v1/auth/logout`. Only `api/v1/auth/login` and `api/v1/auth/register` are public |
| Unknown fields | Servers must ignore unknown request fields. Clients must ignore unknown response fields |
| Trailing slashes | Not used. `api/v1/scans`, not `api/scans/` |

### Error shape

Every non-2xx response uses exactly this shape:

```json
{
  "error": {
    "code": "SCAN_NOT_FOUND",
    "message": "That scan no longer exists.",
    "details": null
  }
}
```

`code` is a stable machine-readable string; `message` is shown to the user, so write it
in plain language. `details` is optional and may carry a field-level map for validation
errors:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "The barcode is required.",
    "details": { "barcode": "must be 1 to 64 characters" }
  }
}
```

| HTTP | When |
| --- | --- |
| 400 | `VALIDATION_FAILED` — malformed body or parameters |
| 401 | `UNAUTHENTICATED` — missing, malformed or expired token |
| 403 | `FORBIDDEN` — valid token, but the resource belongs to another user |
| 404 | `SCAN_NOT_FOUND`, `ITEM_NOT_FOUND`, `USER_NOT_FOUND` |
| 409 | `EMAIL_TAKEN` |
| 429 | `RATE_LIMITED` — include a `Retry-After` header in seconds |
| 500 | `SERVER_ERROR` — never leak a stack trace in `message` |

**A 403 must never be used to reveal that a resource exists.** If a scan belongs to
another user, return `404 SCAN_NOT_FOUND`. Otherwise a user can enumerate other
people's scan IDs by watching which ones give 403 rather than 404.

### CORS

The two front-ends are on different origins from the API, so CORS is required, not
optional:

- `Access-Control-Allow-Origin` — the deployed MyCodeScan origin, the deployed MyStokio
  origin, and `http://localhost:5173` / `http://localhost:5174` for development. Echo a
  matching origin from an allow-list; **do not** use `*` together with credentials.
- `Access-Control-Allow-Headers: Authorization, Content-Type`
- `Access-Control-Allow-Methods: GET, POST, PATCH, DELETE, OPTIONS`
- Answer `OPTIONS` pre-flight with `204`.

### Rate limits

Suggested, not mandatory: 600 requests per minute per user. Item creation is the hot path — a
fast scanner produces one POST per barcode, as it is read — so keep that limit generous or the
app will be throttled during a shelf sweep.

Nothing is lost when it is: the phone queues locally and retries. But a rejected request
becomes a pending count the operator cannot clear, so size the limit for a person scanning
quickly rather than for an average.

## 3. Authentication — the `/api/v1/auth` router

**MyCodeScan has no accounts of its own.** It signs in against the same router MyStokio uses,
so one account works in both apps and a scan made on the phone is readable at the counter.

Auth is mounted at `/api/v1/auth` — `app.use("/api/v1/auth", accountAuthRoutes)`. Four routes:

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| POST | `api/v1/auth/register` | public | create an account, and sign in |
| POST | `api/v1/auth/login` | public | sign in |
| GET | `api/v1/auth/me` | bearer | the signed-in account |
| POST | `api/v1/auth/logout` | bearer | end the session |

Both `register` and `login` answer with the same envelope:

```json
{ "accessToken": "eyJ...", "account": { ... } }
```

**One token, no refresh token.** A session is renewed by signing in again, and whether a
stored token is still usable is decided by reading its own `exp` claim rather than by asking
the server. A `401` therefore means a rejected *token*; rejected *credentials* are also `401`,
and `400` means the request was malformed.

> **An earlier version of this section documented a different router** — `api/auth/login`
> taking a free-text `userId`, `api/auth/register` returning a bare
> `{ "message": "User registered successfully" }` with no token. That is gone. Anything built
> against it will not work.

### There is no guest, demo or anonymous mode

Every scan endpoint requires a real account. A scan session belongs to a user and is read back
by that user at the counter; an anonymous session could be listed and billed by a stranger
pointed at the same server.

Servers must never accept the literal string `"demo-token"` as a credential. It is not
hypothetical — it was manufactured by an earlier client fallback, so it may still arrive. Both
clients now treat it as *no token at all*.

### Token storage keys

Both apps use the same keys, so serving them from one origin shares a single session:

```
stockledger.accessToken
stockledger.refreshToken   (unused — there is no refresh token)
```

### `POST api/v1/auth/register`

Public. Creates the account **and returns a token**, so there is no second call — showing
"account created" followed by a login form reads as a failure.

```json
{
  "name": "Ramesh Kumar",
  "email": "ramesh@shop.com",
  "password": "...",
  "phone": "9876543210",
  "shopName": "Ramesh General Store",
  "plan": "1year",
  "developerCode": "..."
}
```

| Field | Required | Notes |
| --- | --- | --- |
| `name` | yes | |
| `email` | yes | lower-cased and trimmed before storing, so any capitalisation matches later |
| `password` | yes | stored with a slow salted hash — bcrypt, scrypt or argon2 |
| `phone` | no | omitted rather than sent blank |
| `shopName` | no | omitted rather than sent blank |
| `plan` | **yes in practice** | see below |
| `developerCode` | yes | the invite gate — see below |

`201`:

```json
{
  "accessToken": "eyJ...",
  "account": {
    "id": "6a8454525ea6ec85560b2e59",
    "email": "ramesh@shop.com",
    "name": "Ramesh Kumar",
    "phone": "9876543210",
    "shopName": "Ramesh General Store",
    "role": "admin",
    "subscription": {
      "plan": "1year",
      "status": "active",
      "startedAt": "2026-08-19T06:12:44.019Z",
      "expiresAt": "2027-08-19T06:12:44.019Z"
    },
    "createdAt": "2026-08-19T06:12:44.019Z"
  }
}
```

| Case | Response |
| --- | --- |
| Missing fields | `400 { "error": { "code": "VALIDATION_FAILED", "message": "Please check the details entered.", "details": { "email": "is required" } } }` |
| Email already used | `409 { "error": { "code": "EMAIL_TAKEN", "message": "An account with that email already exists." } }` |
| Bad or missing `developerCode` | `403 { "error": { "code": "FORBIDDEN", "message": "That developer code is not valid." } }` |

#### The subscription is mandatory, and is never taken as input

Both clients always send `plan`. The server maps it to dates itself:

| `plan` | Runs for |
| --- | --- |
| `1year` | 365 days — **the default** |
| `2year` | 730 days |
| `lifetime` | no expiry (`expiresAt: null`) |

`expiresAt` must be **computed, never accepted from the client** — a client that could post its
own expiry could grant itself a decade. An unrecognised `plan` falls back to `1year` rather
than to no subscription at all, so an account always has a real expiry.

A **lapsed** subscription still signs in. The app needs the account in order to show a renewal
screen, and locking a shopkeeper out of their own data is a worse answer than telling them what
is wrong. Clients decide expiry by comparing `subscription.expiresAt` to now.

#### `developerCode` — registration is invite-only

Both apps ask for an access key on the signup form and send it as `developerCode`. **The
server must check it.**

The client-side check is only a speed bump: the key is compiled into the JavaScript bundle, so
anyone who opens the page can read it and anyone at all can `POST` to this endpoint directly.
Sending the value is what makes a real gate possible — a backend that ignores `developerCode`
has an open registration endpoint no matter what the form does.

Compare it against a value held in the server's environment, not in the repository, and answer
`403` on a mismatch or an absence. Do not echo the expected value back in the error.

### `POST api/v1/auth/login`

Public.

```json
{ "email": "ramesh@shop.com", "password": "..." }
```

The field is **`email`** — an address, not the free-text user id an earlier version of this
document described. Match it case-insensitively.

`200`: the same `{ accessToken, account }` envelope as register.

| Case | Response |
| --- | --- |
| Missing field | `400 { "error": { "code": "VALIDATION_FAILED", "message": "Email and password are required.", "details": { ... } } }` |
| Wrong password **or** unknown email | `401 { "error": { "code": "UNAUTHENTICATED", "message": "Email or password is incorrect." } }` |

The identical answer for both cases is deliberate and should stay: distinguishing them turns
the endpoint into a way to discover which addresses are registered. Compare a hash even when no
user matched, so the two cases take about the same time to answer — otherwise the timing alone
reveals which emails exist.

> **A flaw to fix, not to copy.** The deployed server was observed returning the bcrypt
> `password` hash inside the account object on login. A password hash has no business leaving
> the database — anyone who captures one response can attack it offline at their leisure. Remove
> that field. The reference implementation deliberately omits it.

### `GET api/v1/auth/me`

Bearer. Answers `200 { "account": { ... } }` with the same account shape, or `401` if the token
is missing, malformed or expired. Used on start-up to decide whether a stored token is still
good.

### `POST api/v1/auth/logout`

Bearer. Answers `200 { "message": "Signed out." }`.

Tokens are stateless, so there is nothing to invalidate — the client discards its copy. The
route exists so both apps have something to call, and so that adding a blocklist later needs no
client change.

Any other path under `/api/v1/auth/` must `404`. Falling through to a catch-all would let a
typo look like a success.

### Error shape

Every auth and scan error uses the nested form:

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "...", "details": { "email": "is required" } } }
```

A stable `code` lets a client treat a missing scan differently from a network failure without
matching on prose, and `message` is shown to the user as written — so write it as a sentence a
shopkeeper would understand.

`details` is optional and maps field name to what is wrong with it. Send only the fields that
actually failed; both clients append them to the message, so a `details` entry for a field that
passed reads as a false accusation.

> **Both clients read the flat `{ "message": "..." }` form too**, because an earlier version of
> this server used it on the auth routes. Keeping that tolerance is cheap. What is not
> tolerable is the reverse: a client that reads only the flat form turns
> "Email and password are required." into the literal text **"[object Object]"** on screen,
> because `error` is an object and `new Error()` stringifies it. That bug shipped once.

## 4. The scan resource

### Shape

```json
{
  "scanId": "SC-7QK2M",
  "label": "Shelf 3 top row",
  "status": "open",
  "deviceName": "Android phone",
  "itemCount": 4,
  "totalQty": 7,
  "createdAt": "2026-08-18T06:14:22.418Z",
  "updatedAt": "2026-08-18T06:31:02.006Z",
  "items": [
    {
      "barcode": "2000000000017",
      "qty": 2,
      "firstScannedAt": "2026-08-18T06:15:01.220Z",
      "lastScannedAt": "2026-08-18T06:20:44.900Z"
    }
  ]
}
```

| Field | Type | Notes |
| --- | --- | --- |
| `scanId` | string | See the format rules below. Immutable |
| `label` | string | Free text, 0–80 chars. May be empty |
| `status` | `"open" \| "ready"` | `open` while scanning; `ready` when the phone user says they are done |
| `deviceName` | string | 0–60 chars, informational — e.g. `"Android phone"` |
| `itemCount` | integer | Number of distinct barcodes. Server-computed |
| `totalQty` | integer | Sum of `qty`. Server-computed |
| `items` | array | **Omitted from list responses.** Present in single-scan responses |

`itemCount` and `totalQty` are server-computed and must be ignored if a client sends
them. They exist so the PC's picker can show "4 items, 7 units" without downloading
every session's contents.

### Item shape

| Field | Type | Notes |
| --- | --- | --- |
| `barcode` | string | 1–64 chars. Whatever the scanner read, trimmed. Not validated as a real barcode |
| `qty` | number | > 0. May be fractional (0.5 kg loose goods), up to 3 decimal places |
| `firstScannedAt` | ISO date | Server-set on creation |
| `lastScannedAt` | ISO date | Server-set on every increment |

Barcodes are stored **as scanned**, not normalised or validated. The server has no
product catalogue and cannot know whether `0000123` and `123` are the same item;
guessing would silently bill the wrong product. Matching is MyStokio's job.

**A barcode is unique within a scan.** Scanning the same code twice increments `qty`
rather than adding a second row. This is what makes the phone usable — a shopkeeper
scanning six identical tins gets one line of six.

### `scanId` format

`SC-` followed by 5 characters from **Crockford base32 without vowels**:

```
0123456789BCDFGHJKLMNPQRSTVWXYZ
```

No `A`, `E`, `I`, `O`, `U` (no accidental words), and no `I`, `L`, `O`, `U` ambiguity
with digits. Total: `SC-` + 5 chars, e.g. `SC-7QK2M`.

Why not a UUID: this ID is read aloud across a shop floor and picked out of a list on a
PC. It must be short and unambiguous. Collisions are handled by retrying generation —
with 31⁵ ≈ 28.6 million combinations and only a shop's worth of live sessions, a retry
loop of a few attempts is sufficient. Scope uniqueness globally, not per user, so an ID
never means two things.

Treat `scanId` as case-insensitive on input (upper-case it) and always return it
upper-case. Somebody will type it in lower case.

## 5. Scan endpoints

All require authentication. **A user may only ever see and touch their own scans.**

### `POST api/scans`

Creates a session. Called when the phone user taps "New scan".

Request (all fields optional):

```json
{ "label": "Shelf 3 top row", "deviceName": "Android phone" }
```

`201`: the full scan object, with `items: []`.

### `GET api/scans`

Lists the caller's sessions, **newest first by `updatedAt`**, without items.

| Query | Type | Default | Notes |
| --- | --- | --- | --- |
| `status` | `open \| ready` | *(all)* | Filter |
| `limit` | 1–100 | 50 | |
| `cursor` | string | — | Opaque; from `nextCursor` of a previous page |

`200`:

```json
{
  "scans": [
    {
      "scanId": "SC-7QK2M",
      "label": "Shelf 3 top row",
      "status": "ready",
      "deviceName": "Android phone",
      "itemCount": 4,
      "totalQty": 7,
      "createdAt": "2026-08-18T06:14:22.418Z",
      "updatedAt": "2026-08-18T06:31:02.006Z"
    }
  ],
  "nextCursor": null
}
```

`nextCursor` is `null` when there are no further pages. Empty list returns
`{ "scans": [], "nextCursor": null }` with `200` — never `404`.

Sorting by `updatedAt` rather than `createdAt` is deliberate: a session someone is
actively adding to should rise to the top of the counter's list.

### `GET api/v1/scans/{scanId}`

The full session **including `items`**. This is what the billing screen calls when the
user picks a session.

`200`: the full scan object.
Errors: `404 SCAN_NOT_FOUND`.

### `PATCH api/v1/scans/{scanId}`

Updates `label` and/or `status`. Both optional; only supplied fields change.

```json
{ "label": "Shelf 3 and 4", "status": "ready" }
```

`200`: the full scan object.

Transitions are unrestricted — `ready` back to `open` is allowed, because someone will
mark a session done and then remember one more item.

### `DELETE api/v1/scans/{scanId}`

Deletes the session and its items.

`204` with no body.

**This must be idempotent: deleting an already-deleted scan returns `204`, not `404`.**
MyStokio calls this automatically after saving an invoice, and may retry after a network
error. A `404` there would surface as a scary error message about a session the user has
already finished with, for an operation that in fact succeeded.

### `POST api/v1/scans/{scanId}/items`

Adds a barcode, or increments it if already present. **The hot path** — called once per
scan on the phone.

```json
{ "barcode": "2000000000017", "qty": 1, "clientItemId": "b1f0c2a4-..." }
```

| Field | Required | Notes |
| --- | --- | --- |
| `barcode` | yes | 1–64 chars after trimming |
| `qty` | no | Defaults to `1`. Must be > 0 |
| `clientItemId` | no | Idempotency key, see below |

`200`: the full scan object, so the phone can re-render from authoritative state
without a second request.

**Idempotency.** The phone queues scans locally and flushes them when the network
returns, so the same request can arrive twice. If `clientItemId` has been seen on this
scan before, the server must **ignore the duplicate** and return the current state
unchanged. Remember at least the last 500 `clientItemId`s per scan. Without this, a
retry after a timeout that actually succeeded silently double-counts stock — the sort of
bug that surfaces a month later as unexplained shrinkage.

### `PATCH api/v1/scans/{scanId}/items`

Sets an exact quantity — used when the phone user corrects a line.

```json
{ "barcode": "2000000000017", "qty": 3 }
```

`200`: the full scan object.
Errors: `404 ITEM_NOT_FOUND` if that barcode is not in the scan.

`qty` of `0` is a validation error, not a delete. Deleting is `DELETE`, so a client
cannot remove a line by accident through an off-by-one.

### `DELETE api/v1/scans/{scanId}/items`

Removes one line. The barcode goes in the body rather than the path, because barcodes
can contain characters that are awkward in a URL segment.

```json
{ "barcode": "2000000000017" }
```

`200`: the full scan object (not `204` — the client needs the new totals).

Idempotent: removing a barcode that is not there returns `200` with the scan unchanged.

## 6a. The phone flow, precisely

Each barcode is sent as it is read. There is nothing to save by hand:

1. `POST api/v1/scans` when the operator starts a scan — the session exists from that moment
   and has an ID the counter can already see.
2. `POST api/v1/scans/{scanId}/items` once per barcode, each with its `clientItemId`, sent
   immediately after the barcode is read.
3. `PATCH api/v1/scans/{scanId}` — `status: "ready"` and the label — when the operator taps
   Done.

The phone writes every scan to local storage *before* sending it, and retries whatever failed
when the connection returns. Two consequences for a server implementation:

- **De-duplication is not optional.** The commonest real failure is a request the server
  accepted whose reply was lost: the phone believes it failed and retries. Without the
  `clientItemId` check in §5, that barcode is counted twice, and nobody notices until a
  stock-take.
- **Empty sessions happen.** A session is created when scanning starts, so one abandoned
  before the first barcode stays empty. The retention sweep in §7 clears them.

## 6b. The billing flow, precisely

This is the sequence MyStokio performs. Getting the order right matters.

1. `GET api/v1/scans?status=ready` — the picker list. (MyStokio actually requests all
   statuses, so a session left `open` is still reachable.)
2. `GET api/v1/scans/{scanId}` — read the items.
3. *Locally*, match each barcode against the shop's own products. Unmatched barcodes are
   **reported to the user, never dropped silently.**
4. The user saves the invoice.
5. `DELETE api/v1/scans/{scanId}` — only now.

**Step 5 comes after step 4, and that is not negotiable.** A tempting alternative is a
single `POST api/v1/scans/{id}/consume` that returns the items and deletes them atomically.
Do not add one. If the invoice then fails to save — a validation error, a closed
browser, a power cut — the barcode list is gone and the shopkeeper must walk the shelves
again. Reading is cheap and idempotent; deleting is destructive and belongs after the
work it enables has succeeded.

If step 5 fails, MyStokio does not block or warn: the invoice is saved, which is what
matters, and the stale session can be deleted from the phone. Servers should therefore
expect sessions that are never explicitly deleted.

---

## 7. Retention

Sessions are working notes, not records. Delete them on a schedule — **30 days after
`updatedAt`** is suggested — and say so in the app's terms. Nothing downstream depends
on an old session, and the alternative is a database that grows forever holding barcode
lists nobody will ever open.

## 8. Implementation checklist

- [ ] Passwords hashed with bcrypt / scrypt / argon2, never a bare digest
- [ ] Same 401 for an unknown email and a wrong password, taking about the same time
- [ ] `{ accessToken, account }` returned by **both** register and login
- [ ] **The password hash absent from every response**
- [ ] `developerCode` checked against an environment value, `403` on a mismatch — the
      client-side check is only a speed bump, since the key ships in the bundle
- [ ] `subscription` always set, dates **computed** from `plan` and never accepted as input
- [ ] An expired subscription still signs in, so the app can show a renewal screen
- [ ] No guest, demo or anonymous path to a token — and `"demo-token"` never accepted
- [ ] An unmatched `api/v1/auth/*` route answers 404, not 401
- [ ] Errors use the nested `{ error: { code, message, details } }` form, with `details`
      naming only the fields that actually failed
- [ ] `404`, not `403`, for another user's scan
- [ ] Every scan query filtered by the authenticated user's id — in the query itself,
      not by checking after fetching
- [ ] `scanId` uniqueness enforced by a unique index, with generation retry on collision
- [ ] `barcode` unique per scan, enforced by a compound unique index
- [ ] `POST api/v1/scans/{id}/items` increments rather than duplicating
- [ ] `clientItemId` de-duplication on item creation
- [ ] `DELETE api/v1/scans/{id}` idempotent — `204` even when already gone
- [ ] `itemCount` and `totalQty` computed server-side and never trusted from a client
- [ ] CORS allow-list covering both front-end origins plus localhost
- [ ] `OPTIONS` answered `204`
- [ ] Timestamps ISO 8601 UTC with `Z`
- [ ] No stack traces in error messages
- [ ] Retention job for sessions older than 30 days

| POST | `api/v1/auth/login` | — | Sign in |

| POST | `api/v1/auth/logout` | ✓ | End the session |
| POST | `api/v1/scans` | ✓ | Start a session |
| GET | `api/v1/scans` | ✓ | List sessions, no items |
| GET | `api/v1/scans/{scanId}` | ✓ | One session with items |
